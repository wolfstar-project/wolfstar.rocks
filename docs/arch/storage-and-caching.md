# Storage and caching

Read before changing Nitro storage mounts or cache drivers.

- On a Worker (`NITRO_PRESET=cloudflare_module`), `modules/cache.ts` puts `cache`, `fetch-cache` and the two rate limiters on Workers KV bindings through `shared/utils/storage/cloudflare-kv-fallback.ts`, which falls back to memory while the binding is not there (the prerender in Node, the plugins before the first request), and skew protection keeps its versions on disk, carried between deploys by the GitHub Actions cache. KV has no compare-and-swap, so the rate limiters' read-modify-write cycles can race across isolates. See [cloudflare-workers](cloudflare-workers.md)
- On a Worker a guild's requests land on many isolates, so two answers each isolate would otherwise fetch again are shared through the `cache` storage (Workers KV) by `server/utils/shared-cache.ts`: the bot's membership probe of a guild (`discord:guild-probe:<id>`, `probeBotGuildMembership()`: a minute when the bot is in the guild, ten minutes when it is not, since the server list probes every guild of the user and the bot is absent from most) and a guild's settings (`settings:guild:<id>`, `SETTINGS_CACHE_MAX_AGE`, `readSettings()`). An entry keeps the time it was read from its source and its reader judges it by that, so the minute KV keeps a read in each location never makes it older than its window. Writes go behind the answer through `waitUntil`, and a failed read or write is a miss. `invalidateGuildCache()` (the `?refresh=true` after the bot is invited) removes the shared probe; each isolate keeps a probe's answer in memory for ten seconds at most, since that removal reaches only the isolate that runs it. That bounds the isolates of the same location; in another location KV may still serve the copy from before the invite for the minute it keeps a read. A bot invited from Discord itself, without the dashboard's invite, shows within ten minutes or on a refresh of the server list. A settings write overwrites the shared copy; the bot's own writes reach it within the window, as they reach the memory cache
- The dashboard keeps the answers of its GET calls in the browser's localStorage (`app/utils/persisted-cache.ts`, keys `wolfstar-cache:<account id>:<asyncData key>`, a day at most): `usePersistedAsyncData()` is `useLazyAsyncData` that serves the stored answer at once on a reload or a return to a section and fetches again behind it, while a manual `refresh()` always fetches. The guild and its settings (`layouts/dashboard.vue`), the account's guilds (`useUser`), the three logs, the reports and the auto-moderation rules go through it. `app/plugins/persisted-cache.client.ts` empties the store when the account signs out or changes. Under test the store is off unless a spec calls `enablePersistedCacheInTests()`, since every browser-mode test file shares one localStorage
