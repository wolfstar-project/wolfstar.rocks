# Cloudflare Workers build

Read before changing `config/cloudflare.ts`, the `isCloudflareBuild` branches of `nuxt.config.ts` and `modules/cache.ts`, `server/database/prisma.ts`, or `server/cloudflare/`.

The site runs on Cloudflare Workers: the Worker `wolfstar-rocks` serves wolfstar.rocks, its `beta` environment serves beta.wolfstar.rocks. Wrangler deploys an environment as a Worker of its own, `wolfstar-rocks-beta`: it takes the top level's `main`, `assets`, compatibility flags and observability, and lists its own bindings, `vars`, `version_metadata` and routes. Local builds and the test builds of CI target Node, unless `NITRO_PRESET` starts with `cloudflare`.

## Build and deploy

- `NITRO_PRESET=cloudflare_module pnpm build`, with `CLOUDFLARE_WORKER=production` for the production Worker or `CLOUDFLARE_WORKER=beta` for its `beta` environment. A Workers build without one of the two fails: no Worker is a safe default. The beta build writes the production Worker's name and only `env.beta`, without production's bindings or domains, so it deploys with `--env beta`. A deploy without the flag does not fail: Wrangler only warns, and uploads beta's build to `wolfstar-rocks` with no bindings, which breaks wolfstar.rocks. Deploy beta only through `deploy-beta.yml`, which passes the flag. Skew protection is given the namespace id of the environment deployed (`SKEW_PROTECTION_NAMESPACE_ID`), since the module looks for its binding at the top level only. Prerendering starts the server, and Better Auth refuses to start in production without a secret, so the build needs some `NUXT_BETTER_AUTH_SECRET`; the Worker's own secret overrides it at run time. Without a Sentry upload token the build makes no client source maps, as nothing would upload and then delete them.
- `npx wrangler deploy -c .output/server/wrangler.json`. Nitro writes that file from `WORKER` in `config/cloudflare.ts`, and it replaces what the Cloudflare dashboard holds: plain variables live in its `vars`, which the build reads too, so the prerendered pages carry that site's public config. Secrets are set with `npx wrangler secret put <NAME> --name wolfstar-rocks` (`wolfstar-rocks-beta` for beta) and outlive each deploy.
- At run time Nitro overrides a runtime config key from the env var named after its path, so the secrets are `NUXT_BETTER_AUTH_SECRET`, `NUXT_DISCORD_BOT_TOKEN`, `NUXT_DISCORD_CLIENT_SECRET`, `NUXT_BOT_API_OAUTH_SECRET` (the members' appeals, through the bot's API; `NUXT_BOT_API_OAUTH_COOKIE` too when the bot names its cookie otherwise) and, for the join guard's verification page, `NUXT_TURNSTILE_SECRET_KEY`, not the `NUXT_OAUTH_DISCORD_*` names the build reads. The Turnstile site key is public, so it is a plain variable: the build lists `NUXT_PUBLIC_TURNSTILE_SITE_KEY` in `vars` when it is given one (a repository variable of the deploy workflows), since a deploy replaces what the dashboard holds. Without it the page offers no captcha, and a server that asks for one cannot verify anybody.
- Skew protection writes the new build's assets to its KV namespace by running `wrangler` during a build in CI (a dev dependency, pinned in the lockfile, which the deploy steps use too), and only when CI sets `SKEW_PROTECTION_BUNDLE_ASSETS=true`, which needs `CLOUDFLARE_API_TOKEN` too: without it the build keeps no past assets.
- Production is deployed gradually. `.github/workflows/deploy.yml` uploads each build as a new Worker version (`wrangler versions upload`, tagged with the commit) and gives it `WORKER_ROLLOUT_PERCENTAGE` percent of the traffic next to the version that served all of it (`wrangler versions deploy new@P% old@(100-P)%`). The `promote` job then waits on the `release-promote` environment, whose required reviewers approve moving the new version to 100%. Rejecting it leaves the split; the deploy job's summary prints the command that sends all traffic back to the previous version. Without the repository variable, or at 100, the new version takes all traffic at once and `promote` is skipped. The Worker's first deploy, with no version to split with, is a plain `wrangler deploy`, which also creates the custom domain. `versions upload` never touches routes or custom domains: a change to `routes` in `config/cloudflare.ts` needs one `wrangler deploy`. A gradual deployment can only use the last 100 uploaded versions.
- Production is built by that workflow on every push to `release`. It reads the repository variables `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_HYPERDRIVE_ID` and `NUXT_OAUTH_DISCORD_CLIENT_ID`, and the secrets `CLOUDFLARE_API_TOKEN`, `NUXT_APP_SECRET`, `NUXT_BETTER_AUTH_SECRET`, `SENTRY_AUTH_TOKEN` and `SENTRY_PROJECT`. The `ci` workflow builds the same Worker on each pull request and checks it with `wrangler deploy --dry-run`.
- Beta is built and deployed by `.github/workflows/deploy-beta.yml` on every push to `main`, all at once. It reads the repository variable `CLOUDFLARE_ACCOUNT_ID` and the secret `CLOUDFLARE_API_TOKEN`, as production does, and makes a throw-away auth secret for the prerender. It shares the database of the WolfStar Beta bot (the beta environment on Railway, through the Hyperdrive `wolfstar-beta`) and signs in with the WolfStar Beta application, whose Discord settings list `https://beta.wolfstar.rocks/oauth/callback` and `/oauth/guild`. Production's sign-in cookies cover the whole `wolfstar.rocks` domain and reach beta too, so beta names its session cookie `wolfstar-session-beta` and the cookie it mints for the bot's API `WOLFSTAR_BETA_AUTH`, which the beta bot's `OAUTH_COOKIE` matches. The build reads the repository secret `NUXT_APP_SECRET_BETA` as `NUXT_APP_SECRET`: og-image signs its URLs with Nuxt's `appSecret` and turns strict mode on only when the build has one, so the Worker's `NUXT_APP_SECRET` holds the same value. Its secrets are set with `--name wolfstar-rocks-beta`: `NUXT_BETTER_AUTH_SECRET`, `NUXT_DISCORD_BOT_TOKEN` and `NUXT_DISCORD_CLIENT_SECRET` of the WolfStar Beta application, and `NUXT_BOT_API_OAUTH_SECRET`, the beta bot's `OAUTH_SECRET`.
- Alpha is built from `refactor/v3` by Workers Builds on Cloudflare (8 GB, 20 minutes): a local build needs more memory than a 4 GB machine has. Build command `(git fetch --quiet --unshallow --tags origin '+refs/heads/release:refs/remotes/origin/release' || git fetch --quiet --tags origin '+refs/heads/release:refs/remotes/origin/release' || true) && pnpm build && find .output/public -name '*.map' -delete`: Workers Builds clones without tags or the `release` branch, and without them `getNextVersion()` finds no `v*` tag and the site shows `package.json`'s `0.0.0`, deploy command `npx wrangler deploy -c .output/server/wrangler.json --autoconfig=false`, build variables `NITRO_PRESET=cloudflare_module`, `NODE_OPTIONS=--max-old-space-size=6144` and the secret `NUXT_BETTER_AUTH_SECRET`. With no `SENTRY_AUTH_TOKEN` the Sentry source map plugins are off, and the Worker is bundled without server source maps: with them, rewriting and collapsing every chunk's map took Nitro's bundling step past the build's time limit. The production Worker is bundled without server source maps too, so its server stacks reach Sentry minified; only the client maps are uploaded.

## Around the Worker

Set on the `wolfstar.rocks` zone, outside this repository:

- **The beta bot's API.** `api.wolfstar.beta.integrations.wolfstar.rocks` routes to the beta bot's port 8582 on Railway, whose `API_ORIGIN` is the beta site, and `wolfstar.beta.integrations.wolfstar.rocks` to its interactions endpoint on port 3000. Both are proxied CNAMEs to Railway custom domains, verified by their `_railway-verify` TXT records.
- **The alpha bot's API.** `api.wolfstar.integrations.wolfstar.rocks` routes to the staging bot's port 8282 on Railway, whose `API_ORIGIN` is the alpha site. It is proxied, so Total TLS gives it an edge certificate, and a Configuration Rule sets its SSL mode to Full, since Railway presents `*.up.railway.app` until it issues the hostname's own certificate. "Allow Nuxt Proxy to API" skips Super Bot Fight Mode for its `/languages` and `/commands`, as it does for production's.
- **Image transformations.** On for the zone, from the zone's own images and the origins listed under Images below.
- **Skew protection.** A Cache Rule keeps 404s under `/_nuxt/` on wolfstar.rocks out of the edge cache.
- **Version affinity.** While two versions share the traffic, each request must reach the version that served the page, or its hashed `/_nuxt/` assets, `builds/latest.json` and the `__nkpv` version cookie answer from the other one. The Worker picks the version from the `Cloudflare-Workers-Version-Key` request header, which two Transform Rules (Modify Request Header, Set dynamic) set on the zone, in this order, the later winning: "Version affinity: visitor", for `http.host eq "wolfstar.rocks"`, sets it to `ip.src`; "Version affinity: signed in", for the same hosts and `http.cookie contains "__Secure-wolfstar-session.session_token"`, sets it to `http.request.cookies["__Secure-wolfstar-session.session_token"][0]`, so a signed-in admin keeps one version across networks. The key is never stored: Cloudflare hashes it to pick a version, and keys already on the new version stay there as its share grows. Neither the module nor the app sets the header, and `__nkpv` cannot be the key, since it names the build and changes with it. Set `WORKER_ROLLOUT_PERCENTAGE` only once both rules are on

## What differs on a Worker

- **Database.** A Worker refuses I/O across requests: a connection opened while serving one request cannot be used by the next. `server/plugins/database.ts` makes a client for each request from the `HYPERDRIVE` binding and sets it as `event.context.database`; `db` in `server/database/prisma.ts` is a proxy that resolves to it through `useEvent()` and Nitro's async context. Its idle connections are never timed out, since that timer would fire in another request; the runtime closes the sockets when the request, and what it handed to `waitUntil`, is done. Hyperdrive's query cache is off, so a setting read back after a save is the saved one.
- **Requests do not wait on each other.** The runtime cancels a request as hung once its own code has nothing left to run, even while the request it waits on is still working, and a cancelled request never lets go of what it holds. So on a Worker (`canWaitOnOtherRequests()` in `server/utils/keyed-lock.ts`) the in-process locks of `createKeyedLock()` and of the settings writes run at once, a settings read does not join one already running, each request gets its own Discord REST client, and Nitro's cached functions, patched in `patches/nitropack@2.13.6.patch`, do not share a call already running for a key. What orders writes there is the database: transactions, and the advisory locks of the rules and the Auto-* tables.
- **Storage.** There is no file system for the `fsLite` mounts. `modules/cache.ts` mounts them on Workers KV through `shared/utils/storage/cloudflare-kv-fallback.ts`, which falls back to memory while the binding is not there: during the prerender in Node, and while the Worker runs its plugins before the first request brings the bindings.
- **Audit.** `server/plugins/evlog-drain.ts` writes each event inside the drain hook, which evlog hands to `waitUntil`, instead of batching it for a timer that would fire outside any request. There is no secondary file journal; the Postgres hash chain is the record.
- **Content.** `@nuxt/content` loads the site's content into the `CONTENT_DB` D1 database.
- **Images.** Nuxt Image uses the `cloudflare` provider, the zone's image transformations, in open mode with an allow list: `cdn.discordapp.com`, `media.discordapp.net` and `cdn.wolfstar.rocks`, plus the site's own hosts `beta.wolfstar.rocks` and `wolfstar.rocks`. Open mode drops the implicit same-zone allowance, so a host missing from the list fails its own images (`/avatars/*.png`) with error 9401.
- **Sentry.** `server/cloudflare/sentry.ts` sets up Sentry's SDK for Workers, and the Node one from `sentry.server.config.ts` is not imported into the entry. Both drop the same expected HTTP errors (`server/utils/sentry-expected-errors.ts`). Events carry the Worker's environment, `production` or `beta`.
- **Skew protection.** It keeps its versions in a KV namespace of its own, `SKEW_PROTECTION`, as the module's Cloudflare guide sets it up. The assets of past deploys (`bundleAssets`) are kept only when a build in CI sets `SKEW_PROTECTION_BUNDLE_ASSETS=true`: the module uploads them one by one through `wrangler`, 25 at a time, which a machine with 4 GB of memory does not survive, and on Workers Builds the upload of the last releases' 626 assets each ran past the 30 minute limit after the bundle was already written. The module, which `@nuxtjs/seo` installs, adds `/_nuxt/*` to `assets.run_worker_first` on the `cloudflare_module` preset and serves an asset recovery endpoint under `/__skew/asset`.
- **Left out.** `nuxt-studio`, which only runs in development. The `isr` route rules have no effect on Workers.

## Moving production to the Worker

Netlify keeps serving wolfstar.rocks until these are done, in this order. The first push to `release` after them deploys the Worker.

1. Create the Hyperdrive `wolfstar` on production's database, with query caching off, and set its id as `CLOUDFLARE_HYPERDRIVE_ID`.
2. Set the repository variables and secrets the deploy workflow reads, using the same `NUXT_OAUTH_DISCORD_CLIENT_ID` as Netlify, and the Turnstile widget's public `NUXT_PUBLIC_TURNSTILE_SITE_KEY` for the join guard. The `CLOUDFLARE_API_TOKEN` needs Workers Scripts, Workers KV, D1, Hyperdrive and Workers Routes edit on the account and zone.
3. Set the Worker's secrets with `npx wrangler secret put <NAME> --name wolfstar-rocks`: `NUXT_BETTER_AUTH_SECRET` with the value Netlify holds, or every session ends, `NUXT_APP_SECRET` with the value of the repository secret of the same name, which the build signs og-image URLs with, plus `NUXT_DISCORD_BOT_TOKEN`, `NUXT_DISCORD_CLIENT_SECRET`, `NUXT_BOT_API_OAUTH_SECRET` and `NUXT_TURNSTILE_SECRET_KEY`.
4. Turn off the zone's managed transform `remove_visitor_ip_headers`. With it on, a Worker sees no visitor IP, and every visitor shares one rate limit bucket.
5. Move the redirects `netlify.toml` held to Redirect Rules on the zone: `repo.wolfstar.rocks/*` to the GitHub repository, `chat.wolfstar.rocks` to the Discord invite, `social.wolfstar.rocks/twitter` to X, and `blog.wolfstar.rocks/*` to `wolfstar.rocks/blog/*`.
6. Remove the `wolfstar.rocks` DNS record that points at Netlify, and detach alpha.wolfstar.rocks from `wolfstar-alpha`, so the deploy can add the two custom domains, and take the Worker's first deploy from `release`. Keep the `wolfstar-alpha` Workers Builds paused until alpha.wolfstar.rocks is dropped from `wolfstar-rocks`: `ALPHA_WORKER` still lists that domain, and its next build would claim it back.
7. Add the Cache Rule that keeps 404s under `/_nuxt/` out of the edge cache, as alpha has it.
8. Check sign-in, a settings save and an image from `cdn.discordapp.com` on wolfstar.rocks, then stop Netlify's builds.
9. For gradual deployments: add the two version affinity Transform Rules, create the `release-promote` environment with its required reviewers, and set the repository variable `WORKER_ROLLOUT_PERCENTAGE` (for example `10`). Alpha keeps deploying all at once from Workers Builds; to roll it out gradually too, set its deploy command to `npx wrangler versions upload -c .output/server/wrangler.json` and move the version up from the Worker's Deployments page.
