# Nuxt 5

Read before touching `nuxt.config.ts`, `modules/`, `config/`, `server/`, or `test/e2e/`.

The app runs on Nuxt 4.7 with `future.compatibilityVersion: 5`, and builds its server with Nitro v3 and h3 v2: Nuxt 4.7 picks Nitro v3 (`@nuxt/nitro-v3-server`) because `package.json` depends on `nitro`. Removing that dependency switches back to Nitro v2 (nitropack), which this server code no longer runs on. Nitro v3 is still a release candidate, so `nitro` is pinned to an exact version and moves only on purpose. The move follows the Nuxt 5 nightly trial in #600, and the code is written for Nuxt 5, which builds on the same Nitro v3.

- Nuxt 5 turns on `typedPages`, `routeTypedFetch`, `payloadExtraction: "client"`, `inlineErrorRendering`, `navigateToEarlyReturn`, `extractSerializablePageMeta`, `normalizePageNames`, `watcher: "builder"`, case-sensitive routing and `useState` reset-on-clear. Never repeat those in `experimental`. Add only flags Nuxt 5 leaves off (`early404`, `strictRouteTypes`) or deliberate overrides. Compatibility version 5 also turns on `experimental.viteEnvironmentApi`, Storybook and Vitest included; do not turn it off, since Nuxt 5 removes the flag.
- Keep `nitroLegacy: false`. Application server code imports portable helpers from `nuxt/server`. Nitro-specific handlers, hooks, caches and storage use `nitro/h3`, `nitro`, `nitro/cache` and `nitro/kv`. Import nested `server/utils` helpers explicitly. Third-party modules can still receive Nuxt’s automatic compatibility layer.
- Nitro-specific event types come from `nitro/h3`. Read the request from `event.req`, never `event.node`. Declare application context fields on `H3EventContext` in `declare module "h3"`, which `nitro/h3` re-exports. Response headers take strings.
- Nitro v3 gives server code no global `$fetch`. Call a route of this app with `serverFetch(event, path)` from `nuxt/server`, and another URL with `$fetch` from `ofetch`. The build warns with `NUXT_B9011` where a file still calls the global.
- Nitro v3 runs the server plugins one after another and waits for each one, in order: the plugins in `nitro.plugins` of `nuxt.config.ts`, then the modules' plugins, then `server/plugins/`. A hook therefore runs after the hooks of every plugin before its own, async or not. `server/early-plugins/evlog-expected-errors.ts` must lower the level before evlog's `error` hook emits the event, so `nitro.plugins` lists it and `server/plugins/` does not hold it.
- nuxt-i18n-micro reads the dictionaries in production from the `public/` one level above its own file, and Nitro v3 bundles it into `server/_libs/_nuxt/`. `patches/nuxt-i18n-micro@4.1.3.patch` walks up to the `public/` that holds them; without it the server-rendered pages show raw keys such as `footer.tagline`.
- Nitro v3 keeps a cached function's entry under a key ocache builds from its group, name and call key, and it escapes and hashes the group `nitro/functions`. `server/utils/discord/cache.ts` reads the keys from ocache's `resolveCacheKeys()` instead of spelling them, and `nitro.cache.driver` is `"kv"` so those entries sit in the KV storage it removes them from: Workers KV on the Worker (the `cache` mount), memory elsewhere. Without that setting a build with no `cache` mount uses ocache's own memory store, which only the cached function can reach. `test/unit/server/utils/discord/cache.spec.ts` checks the keys against what a real ocache store writes.
- `@nuxt/test-utils` 4.4 takes the h3 of `registerEndpoint` from Nitro v2's integration. `patches/@nuxt__test-utils@4.4.0.patch` resolves `nitro` from the app first, so the stubbed endpoints get h3 v2's event, as the server code does.
- knip's Nuxt plugin reads the server auto-imports only from Nuxt 4's `.nuxt/types/nitro-imports.d.ts`. `knip.ts` lists Nuxt 5's `.nuxt/types/server-imports.d.ts` as an entry, or every helper under `server/utils/` reads as unused.
- Nitro v3 runtime hooks receive a bare `HTTPEvent` in their types. Narrow it with `isEvent(event)` before reading `event.context`. `afterResponse` is now `response`, which takes `(response, event)`.
- A cached handler's `getKey` is typed with the same bare event. `defineWrappedCachedResponseHandler` takes a `getKey` of the route's `H3Event` and narrows the event for it.
- Nitro v3's cached handler answers with `public, max-age, s-maxage`, which lets a shared cache keep the response. A route with `auth` or `authorize` answers for one member, so `defineWrappedCachedResponseHandler` sends it with `private, no-store`, after the Nitro cache has stored the data. h3 stages the cache's header on `event.res` and merges it into the response, so the wrapper sets both.
- In h3 v2, the route a request matched is `event.context.matchedRoute.route`. The rate limiter keys on it; `.path` no longer exists, so a key read from it would fall back to the URL and give each ID its own counter.
- Nitro v3 config names: `kv` (was `storage`), `oxc` (was `esbuild`), `rolldownConfig` (was `rollupConfig`), and `redirect.status` (was `redirect.statusCode`). `nitro.replace` takes source text, so a boolean goes through `JSON.stringify()`.
- Nitro v3 prerenders a redirect route as a bare `<meta http-equiv="refresh">` page, which html-validator refuses. A redirect route rule sets `prerender: false`, and the server answers with the real status.
- nuxt-security augments only `nitropack/types`. `modules/nitro-route-rules.d.ts` declares its `security` key, and the `robots` key, on `RouteRuleConfig` of `nitro/types`.
- `@nuxt/content` depends on h3 v1. `pnpm-workspace.yaml` overrides it to h3 v2, which changes only its types: at runtime Nuxt applies its compatibility layer to the module’s legacy code. Nuxt 5 writes the server TS project itself, so `typescript.serverTsConfig.include` lists `./content/types.d.ts`; without it `queryCollection()` in server routes resolves to `never`. `typescript.sharedTsConfig.include` lists it for the same reason, since typed `$fetch` pulls server handlers into the `shared` project.
- Nuxt's typed `$fetch` takes the response type as its only explicit type argument. Never pass `string` and a method after it (`$fetch<T, string, "PUT">`): the call then matches no signature of Nuxt's `$fetch`.
- Because routing is case-sensitive and `early404` 404s any path no page or alias can match before the Vue app boots, new entry points must be real pages or `definePageMeta` aliases, not router middleware redirects from unknown paths.
- Nuxt 5 generates `.nuxt/tsconfig.node.json` with `module`/`moduleResolution: "nodenext"` and `erasableSyntaxOnly`, and loads `nuxt.config.ts` and local modules natively in Node before falling back to jiti (`NUXT_B5023`/`NUXT_B8023` warnings). Relative imports in `nuxt.config.ts`, `modules/`, `config/` and `test/e2e/` therefore need explicit `.ts` extensions, JSON imports need `with { type: "json" }`, and directory imports must name the file.
- Many modules still ship Nitro v2 server code. The build lists them under `NUXT_B9002` (handlers without a route, registered as middleware on `/**`) and `NUXT_B9003` (the layer applied to their code). Those warnings belong to the modules.

- `config/runtime.ts` generates build-time defaults for Nuxt and Sentry. `server/utils/runtimeConfig.ts` reads runtime overrides through `nuxt/server`. Never import runtime server helpers into the build-time generator.
- Native `defineCachedHandler` returns a serialized `Response`. The wrapper retains its resolver’s body type for typed API callers. Authorization stays outside the cache and runs on every hit.
- Native async context exposes `useRequest()` from `nitro/context`. `new H3Event(useRequest()).context` reads the request’s shared context for database and Discord clients.

- `patches/nuxt-studio@1.8.2.patch` corrects the module’s media utility import. The published path leaves the package directory. The patch uses `./runtime/utils/media.js`, which Node can resolve without jiti.
- YAML’s Node export is CommonJS. `nuxt.config.ts` aliases `yaml` to its published ESM build under `browser/`. This keeps `require()` out of the development module runner.
- Nuxt’s Vite client environment declares the application entry. Storybook removes that input so its builder can emit `iframe.html`. Keep the environment’s manifest settings for Nuxt’s asset hooks.
- Nitro v3 exposes Worker bindings through `event.req.runtime.cloudflare.env`. The database plugin reads Hyperdrive there before creating each request’s client.
